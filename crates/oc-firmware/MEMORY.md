# Memory layout of the Teensy 4.0 firmware

## Where the layout comes from

There is **no `memory.x` in this crate, on purpose.**

`teensy4-bsp` is built with the `rt` feature, and its build script drives
`imxrt-rt::RuntimeBuilder`, which generates a complete linker script named
`t4link.x` into `OUT_DIR`. That script defines the memory regions *and* the
i.MX RT boot sections (FlexSPI Configuration Block, Image Vector Table, boot
data). Adding a hand-written `memory.x` would either be ignored or silently
conflict with the generated regions, so the layout is documented here instead
of being duplicated.

The linker is pointed at the generated script from `.cargo/config.toml`:

```toml
[target.thumbv7em-none-eabihf]
rustflags = ["-C", "link-arg=-Tt4link.x"]
```

## Layout produced for the Teensy 4.0

Board-level figures (flash, RAM totals, CPU) match the
[PJRC Teensy technical specifications](https://www.pjrc.com/teensy/techspecs.html).
FlexRAM bank split and section placement below come from `teensy4-bsp` /
`imxrt-rt`, not from that page alone.

FlexRAM on the i.MX RT1062 is 512 KiB of configurable banks. The BSP splits it
as 6 banks ITCM / 10 banks DTCM / 0 banks OCRAM, and uses the dedicated 512 KiB
OCRAM for the heap and uninitialised data.

| Section         | Address       | Memory | Size    | Contents                                     |
|-----------------|---------------|--------|---------|----------------------------------------------|
| `.boot`         | `0x6000_0000` | FlexSPI flash | 8 KiB   | FCB (`FCFB` magic), IVT, boot data     |
| `.text`         | `0x0000_0000` | ITCM   | 192 KiB | code, executed at zero wait state            |
| `.stack`        | `0x2000_0000` | DTCM   | 16 KiB  | main stack, **lowest** DTCM addresses        |
| `.vector_table` | `0x2000_4000` | DTCM   | 1 KiB   | relocated interrupt vector table             |
| `.data`/`.bss`  | above         | DTCM   | 320 KiB | mutable statics                              |
| `.rodata`       | `0x2020_0000` | OCRAM  | —       | constants                                    |
| `.uninit`       | `0x2020_0000` | OCRAM  | —       | uninitialised buffers                        |
| `.heap`         | `0x2020_0000` | OCRAM  | 16 KiB  | heap (currently unused, no allocator)        |

Total flash budget is **1984 KiB**, the size of the Teensy 4.0 application
partition; `cargo xtask flash` refuses images that exceed it.

Run `cargo xtask size` for the current figures. That command prints a selective
section table (runtime sections only — DWARF is omitted on purpose) and runs an
automated layout checklist; it exits non-zero if any hard placement invariant
fails. The flash *loadable* size is reported separately by
`cargo xtask flash --dry-run`, not by the naive `llvm-size` total.

## Stack overflow protection

The plan called for [`flip-link`](https://github.com/knurling-rs/flip-link).
It is **not** used, because it requires a `MEMORY { RAM : ... }` region and
aborts with `MEMORY.RAM not found after scanning linker scripts` against the
ITCM/DTCM/OCRAM regions generated by `imxrt-rt`.

It is also unnecessary here: `flip-link`'s only guarantee is that the stack
sits *below* static data so that an overflow hits unmapped memory instead of
silently corrupting statics. `imxrt-rt` already places `.stack` at
`0x2000_0000`, the very bottom of DTCM, with `.vector_table`, `.data` and
`.bss` above it. The stack grows downwards out of DTCM and immediately faults.
The property is checked automatically by `cargo xtask size` (checklist item
`stack-below-vector-table`): `.stack` must remain at the DTCM base and end at or
before `.vector_table`, with no overlap.

Stack size is 16 KiB and can be overridden at build time through the
`TEENSY4_STACK_SIZE` environment variable honoured by the BSP build script.
